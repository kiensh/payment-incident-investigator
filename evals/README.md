# Evaluation protocol

`dev/scenarios.yaml` contains offline development specifications; `expected/dev.json` contains manually authored expectations. These files are not copied into SQLite or `web/dist`, and no runtime tool can read them. The expected answers are not generated by the production analyzer.

`python -m evals.run` calls `POST /api/investigate` through FastAPI's TestClient. It is the application's real entry point, not a separate imitation of the agent. Each incident gets a temporary database and fresh application, snapshot and tool session. Model-request reservations remain shared across the session to honor the budget.

Scoring checks payment state, appropriate disposition (including cases that require no escalation), required/forbidden rules, manually specified claim text plus supporting evidence IDs, valid citations, safe next checks and consulted procedures. A separate non-production support auditor checks capture/authorization monetary claims against the amounts, currencies, identities and statuses in their cited records; it also rejects new summary prose and verifies returned evidence against the original input snapshot. A mutation test inserts a false999 USD claim with valid IDs and must fail. This narrow claim-grammar check is not a complete semantic-entailment engine: temporal/causal conclusions still need the independent incident oracle and human-reviewable inspection. Reports preserve every returned explanation/trace; valid-looking citation IDs alone do not prove support. Infrastructure failures are listed separately and do not inflate answered-case accuracy. An empty selection is an error.

The mock mode is a **rules-only baseline**. Since authoritative facts are deterministic in both modes, a tied fact score is expected and is not evidence that the LLM adds value. Live evaluation additionally exercises native model tool calls, relevant retrieval, bounded grounded selection and protocol/error handling. Agent value in question relevance and support workflow remains a pilot hypothesis.

## Independent hold-out

A newly created verification agent, not the implementation context, must author approximately ten incident-level hold-out cases after the initial candidate is frozen. It receives the written requirements, code/schemas, candidate commit and setup interfaces, not implementation claims or a proposed verdict. It must not use the dev generator to manufacture expectations or just rename development rows. Compose independently varied evidence shapes/order/coverage and manual expected support/disposition. The runtime sees only observations.

The verifier may write `holdout/*`, `expected/holdout.json` and verification reports, but may not patch implementation. It runs its cases on the frozen candidate and reports reproducible findings. The coordinator fixes implementation and submits a new candidate. If hold-out findings inform fixes, the same cases thereafter are **regression cases**, not untouched hold-out evidence; record this explicitly and use a fresh verifier for the final check.

The first frozen candidate `6de2098` scored7/10 on independently authored cases in `holdout/prepare.py`, with manually specified expectations in `expected/holdout.json`. Its three failures informed fixes, so **these ten cases are now exposed regression evidence, not untouched hold-outs**. The7 baseline-passing cases were also run live once (24 model requests). Exact commands, findings and limits are recorded in `docs/verification.md`.

A second fresh verifier authored five more cases under `final_holdout/prepare.py`. Their original oracle in `expected/final_holdout.json` remains unchanged and scores3/5. A later fresh integrated verifier independently adjudicated two disputed expectations (mandatory escalation for compatible partial/pending captures; a procedural rule ID mistaken for an asserted discrepancy). The separately labelled `expected/final_adjudicated.json` scores5/5 while retaining the financial distinctions, required checks and prohibitions on unsupported claims. These five cases are also exposed regressions, not untouched hold-outs.

Reproduce the supported regression suite without inference:

```sh
uv run python -m evals.holdout.prepare --database artifacts/h-regression.sqlite
uv run python -m evals.run --mode mock --database artifacts/h-regression.sqlite \
  --expected evals/expected/holdout.json --output artifacts/h-regression.json
uv run python -m evals.final_holdout.prepare --output artifacts/f-regression.sqlite
uv run python -m evals.run --mode mock --database artifacts/f-regression.sqlite \
  --expected evals/expected/final_adjudicated.json --output artifacts/f-adjudicated.json
```

Using `final_holdout.json` instead intentionally reproduces the preserved original3/5 result. See `docs/FINAL_VERIFICATION.md` for exact final coverage.
